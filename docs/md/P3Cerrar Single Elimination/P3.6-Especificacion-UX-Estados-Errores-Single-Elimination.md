## 1. Qué es P3.6

P3.2–P3.5 cerraron principalmente la verdad funcional del motor:

```text
P3.2 → BASIC, seeding, pairing, BYEs, target, standings
P3.3 → series, BO1/3/5/7/9, FIXED_GAMES, sudden death
P3.4 → ADVANCED, Structure Graph, fingerprint, liveness, K→Q
P3.5 → Results, Exits, eliminaciones, ON_ELIMINATION, emissions
```

P3.6 tiene otra responsabilidad:

> **Hacer que la interfaz explique fielmente el estado y las capacidades reales del motor.**

No será solo “hacerlo más bonito”. Debe conseguir que el usuario pueda responder sin conocer el código:

- ¿Está guardada mi configuración?
- ¿Es válida?
- ¿Puedo ejecutarla?
- Si no, ¿qué está mal?
- ¿Qué debo hacer después?
- ¿Qué opción está disponible, requiere ADVANCED o está “Próximamente”?
- ¿Qué ocurre en una serie?
- ¿Qué significa un BYE?
- ¿Quién clasificó y quién fue eliminado?
- ¿Qué decisión manual falta?
- ¿Qué perderé si reinicio, elimino o reemplazo algo?

Principio:

```text
Backend / Runtime
       ↓
debe tener una representación fiel
       ↓
Controles + estados + mensajes + acciones
```

---

## 2. Qué NO hará P3.6

P3.6 no debe transformarse en otro sprint de motor. No corresponde añadir aquí:

- Double Elimination;
- League;
- motor Custom genérico;
- nuevas reglas competitivas;
- rollback de resultados propagados;
- histórico persistente;
- Tournament Runtime persistente;
- estadísticas históricas definitivas;
- nuevas semánticas de routing.

Si una pantalla necesita una capacidad fuera de Stable V1:

```text
Próximamente
```

o:

```text
No disponible con esta configuración
```

Nunca se inventará un fallback silencioso.

---

## 3. Principios UX

### 3.1 Truthful UX

Una opción que parezca disponible debe tener:

```text
persistencia + validación + runtime + feedback
```

### 3.2 Qué / por qué / solución

Todo error debe intentar explicar:

1. qué está mal;
2. por qué;
3. qué hacer.

Evitar:

```text
Configuración inválida
```

Preferir:

```text
El modo Básico solo admite Bolsa común.
Cambia la entrada a Bolsa común o utiliza el modo Avanzado.
```

### 3.3 Error, Warning y Recommendation son distintos

```text
ERROR          → bloquea algo importante
WARNING        → puede continuar, pero existe riesgo/condición
RECOMMENDATION → mejora sugerida, no altera validez
```

### 3.4 El color nunca será la única señal

Cada estado tendrá texto, color y explicación.

### 3.5 No saturar

Se mantendrá el lenguaje visual actual de OmniMerge:

- tarjetas redondeadas;
- slate/violet/amber/indigo/fuchsia;
- inspector overlay;
- bloques;
- microcopy breve;
- panel de problemas;
- modales solo para acciones importantes.

## 5. Problema actual: todavía hay confirmaciones nativas

### Competition Lab

Actualmente `resources/js/tournaments/lab/competition-lab.js` contiene un `confirm()` para:

Ese es exactamente el tipo de cuadro nativo del navegador que P3.6 debe eliminar.

### Tournament Graph Flow Builder

```js

```

## 6. Política P3.6: cero `confirm()` normal del navegador

En el flujo normal de OmniMerge:

```text
NO confirm()
NO window.confirm()
NO prompt()
NO alert() como UX principal
```

Acciones destructivas o de pérdida de trabajo:

```text
→ OmniConfirm
```

Ejemplos:

- reiniciar Lab;
- eliminar Phase Exit;
- eliminar encuentro;
- eliminar ruta;
- regenerar/reemplazar estructura;
- descartar cambios;
- abandonar una pantalla con cambios sin guardar.

---

## 7. Extender OmniConfirm para acciones JavaScript

El `OmniConfirm` actual está orientado principalmente a `<form>`.

P3.6 debe reutilizar el mismo modal para acciones JavaScript:

```text

```

Conceptualmente:

```js
OmniConfirm.open({
    title,
    message,
    detail,
    variant,
    actionLabel,
    onConfirm,

```

No debe crearse:

```text
OmniConfirm2
```

ni otro modal separado con diseño diferente.

## 9. Caso especial: `beforeunload`

Actualmente el workspace usa `beforeunload` para proteger cambios sin guardar.

Eso NO es lo mismo que usar `confirm()` manualmente.

Los navegadores modernos controlan ese diálogo por seguridad y no permiten personalizar completamente:

- HTML;
- colores;
- botones;
- contenido;
- estilo.

### Decisión

```text
Navegación interna de OmniMerge
→ Modal OmniMerge

Descartar cambios
→ Modal OmniMerge

Reset
→ Modal OmniMerge

Cerrar pestaña / F5 / cerrar navegador
→ beforeunload nativo como último fallback
```

La meta es que el cuadro nativo **no aparezca durante el uso normal de la aplicación**. Solo podrá aparecer en acciones que el navegador reserva para sí mismo.

## 10. Modal de cambios sin guardar

Si `dirty === true` y el usuario intenta ir a otra pantalla de OmniMerge:

```text

Si sales ahora, volverás a la última configuración guardada.

[Seguir editando]
[Descartar y salir]
```

El botón `Descartar` de la configuración debe usar el mismo patrón cuando haya cambios reales.

## 13. Estados del Structure Graph

Estados Stable V1:

```text
NOT_GENERATED
GENERATED
VALID
INVALID
STALE
BLOCKED
```

Cada uno debe tener nombre, color, explicación y CTA.

| Estado | UX | Acción |
|---|---|---|
| NOT_GENERATED | Sin estructura | Generar estructura |
| GENERATED | Pendiente de validación | Validar |
| VALID | Lista para ejecutar | Probar en Lab |
| INVALID | Contiene errores | Revisar errores |
| STALE | Desactualizada | Regenerar / revalidar |
| BLOCKED | Válida, pero no ejecutable | Ver bloqueo |

### BLOCKED

No debe verse como verde/listo.

Mensaje:

```text
La estructura es coherente, pero utiliza una capacidad
que Stable V1 todavía no puede ejecutar.
```

## 14. Correcciones concretas detectadas en la UI actual

### 14.1 BLOCKED sin estilo propio

La tarjeta principal de Single Elimination tiene estilos propios para:

```text
VALID / INVALID / STALE / GENERATED
```

pero `BLOCKED` cae en el estilo genérico.

P3.6 debe darle identidad visual propia.

### 14.2 “Grafo interno válido” cuando no es ejecutable

El diagnóstico interno puede mostrar verde:

```text
Grafo interno válido
```

aunque:

```text
validation.executable == false
```

y luego añadir un texto secundario.

Debe cambiar a una presentación de `BLOCKED`, no a una tarjeta principal verde.

### 14.3 Warnings etiquetados como recomendaciones

`single-elimination-diagnostic.blade.php` actualmente presenta `warnings` bajo “Recomendaciones”.

P3.6 debe separarlos.

## 23. BYE

UX correcta:

```text

Avanza por BYE
No disputó encuentro.
```

No:

```text
P1 1–0 BYE
```

- no muestra score;
- no muestra botón “Guardar resultado”;
- no cuenta como partido jugado;
- puede mostrar un badge propio.

## 24. Match states

Diferenciar:

```text

PENDING   → Listo para resolver

```

Cuando sea posible:

```text
WAITING
1 de 2 slots completos
```

WAITING no debe pintarse como error.

```text

```

y renderizar:


## 26. Champion y Runner-up

### Champion

Solo:

```text

```

### Runner-up

Solo si se disputó una final real:

```text
2 → 1
```

Una fase `8 → 2` termina con dos clasificados, no con campeón/subcampeón.

## 28. Decisiones manuales

`AWAITING_DECISION` debe ser una tarea prioritaria y visible.

Mostrar:

```text
Decisión necesaria para continuar
```

y bloquear acciones incompatibles.

### Selección exacta

```text
Debes elegir exactamente 2 participantes
1 / 2 seleccionados
```

`Confirmar y continuar` debe permanecer disabled hasta alcanzar el payload válido.

### Orden

Mostrar posición explícita:

```text
Seed 1 · P3
Seed 2 · P1
...
```

cuando el tipo de decisión sea seeding/order.

### Decisión stale

Mensaje útil:

```text
Esta decisión ya no pertenece al estado actual de la fase.
Actualiza el Lab y resuelve la nueva decisión.
```

## 52. Casos QA obligatorios

### Cambios sin guardar

1. Modificar seeding.
2. No guardar.
3. Abrir Estructura.
4. Debe aparecer OmniConfirm.
5. Cancelar → permanecer.
6. Descartar → navegar.

### Reset Lab

1. Ejecutar resultados.
2. Reiniciar.
3. NO debe aparecer cuadro nativo.
4. Sí debe aparecer OmniConfirm.
5. Cancelar conserva estado.
6. Confirmar reinicia temporalmente.

### STALE

1. Generar y validar.
2. Cambiar regla competitiva.
3. Guardar.
4. Estructura → STALE.
5. Lab no debe verse listo.

### BLOCKED

1. Estructura coherente pero no ejecutable.
2. Mostrar BLOCKED.
3. No verde.
4. Explicar capacidad bloqueante.

### BO5

1. Serie 1–0.
2. Mostrar Game 2 y score de serie.
3. Terminar 3–1.
4. No mostrar Game 5 pendiente.

### FIXED4

1. Terminar 2–2.
2. Mostrar “Desempate necesario”.
3. Game extra marcado como desempate.

### BYE

1. Participante obtiene BYE.
2. “Avanza por BYE”.
3. Sin score.
4. Sin acción Guardar.

### Survivor band

1. Ejecutar 8 → 2.
2. Ambos supervivientes: 1.º–2.º.
3. Ninguno: Campeón/Subcampeón.

## 54. Regla específica sobre la “ventana negra”

La decisión queda cerrada así:

```text

→ Modal OmniMerge

Acción destructiva
→ Modal OmniMerge

Reset Lab
→ Modal OmniMerge

Descartar cambios
→ Modal OmniMerge

Navegar internamente con cambios sin guardar
→ Modal OmniMerge

Cerrar pestaña / F5 / cerrar navegador con cambios
→ aviso beforeunload controlado por el navegador
```

El último caso no puede estilizarse de manera fiable por limitaciones de seguridad del navegador. P3.6 reducirá esa experiencia nativa al mínimo práctico.
