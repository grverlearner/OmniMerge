# 1. Propósito de este documento

Este documento constituye el primer entregable formal de **P3 — Cierre definitivo de Single Elimination**.

Su objetivo no es implementar todavía nuevas funcionalidades ni modificar el motor. Su función es establecer una fotografía técnica verificable del estado actual de Single Elimination dentro de OmniMerge y determinar, con el mayor grado de precisión posible, qué partes:

- existen;
- están persistidas;
- están validadas;
- tienen vista previa;
- son ejecutadas realmente;
- funcionan en modo básico;
- funcionan en modo avanzado;
- se integran con Competition Lab;
- se integran con Tournament Graph;
- tienen pruebas automáticas reales;
- requieren pruebas adicionales;
- presentan decisiones semánticas todavía abiertas;
- presentan riesgos antes de declarar el motor estable.

El resultado esperado de P3.0 no es:

> “Single Elimination está terminado”.

El resultado esperado es:

> “Sabemos exactamente qué existe, cómo funciona, qué falta demostrar, qué decisiones deben formalizarse y qué trabajo es necesario para declarar Single Elimination Stable V1”.

## 4.1. Qué significa “verificado en código”

Significa que existe una ruta de implementación explícita que realiza el comportamiento descrito.

No significa necesariamente que el comportamiento haya sido ejecutado en todos sus casos límite durante esta auditoría.

## 4.2. Qué significa “cubierto por tests”

Solamente se considerará cubierto cuando exista una prueba automática con aserciones relevantes.

Un archivo de test que contiene únicamente:

```php
$this->assertTrue(true);
```

se considera infraestructura preparada, pero **no cobertura funcional**.

## 4.3. Qué queda para validación dinámica

Durante P3 se deberán ejecutar escenarios reales y tests para comprobar:

- comportamiento completo de extremo a extremo;
- cantidades irregulares;
- combinaciones de configuración;
- errores;
- routing;
- decisiones manuales;
- integración con Tournament Graph;
- paridad BASIC/ADVANCED;
- regresiones.

Por ello, este documento no utiliza la palabra “completo” únicamente porque exista código.

# 8. Modos de configuración

Actualmente existen:

```text
BASIC
ADVANCED
```

## 8.1. BASIC

Representa el comportamiento automático tradicional de Single Elimination.

El motor genera rondas, BYEs, pairings, avance y finalización.

## 8.2. ADVANCED

Representa una estructura interna explícita y persistente.

El runtime no debe inventar automáticamente la estructura, sino ejecutar la definida por el usuario.

En Competition Lab existe una protección importante:

```text
ADVANCED + estructura activa
    → ejecutar SingleEliminationGraphRuntime

ADVANCED + sin estructura activa
    → rechazar ejecución
```

### Evaluación P3.0

| Área | Estado |
|---|---|
| Distinción BASIC/ADVANCED | ✅ |
| Persistencia | ✅ |
| Routing a runtimes distintos | ✅ |
| Protección de ADVANCED sin estructura | ✅ |
| Paridad semántica entre ambos modos | ⚠️ |
| Cobertura de tests completa | ❌ |

La existencia de dos runtimes no es un problema.

El riesgo aparece si conceptos compartidos significan cosas diferentes en cada uno.

P3 deberá revisar especialmente series, BYEs, outputs, eliminaciones, standings, finalización, selección, errores y routing.

# 13. Modo de finalización

Existen:

```text
WINNER
SURVIVORS
```

## WINNER

El servicio normaliza:

```text
target_survivors = 1
```

## SURVIVORS

Permite definir `target_survivors`.

En BASIC el request exige que el objetivo sea potencia de dos:

```text
1, 2, 4, 8, 16, 32...
```

y que:

```text
target_survivors < participantes efectivos
```

Esta es una protección importante porque evita objetivos estructuralmente imposibles en un bracket binario básico.

P3 deberá probar cantidades iniciales no potencia de dos, objetivos 2 y 4, interacción con BYEs, ADVANCED K → Q y exits.

**Estado: ✅ validación base / ⚠️ requiere suite de escenarios.**

# 16. BYEs

Los modos actuales son:

```text
TOP_SEEDS
RANDOM
MANUAL
```

En BASIC se calcula:

```text
round_size = siguiente potencia de dos
bye_count = round_size - participantes
```

solamente para la primera ronda automática.

### TOP_SEEDS

Ordena por seed y asigna BYE a los primeros.

### RANDOM

Usa ordenamiento determinista por hash.

### MANUAL

Exige exactamente la cantidad necesaria.

### Comportamiento runtime

Un match con un único participante es convertido automáticamente a `BYE`, recibe winner y no genera loser. Además, enviar score a un BYE es rechazado.

Stable V1 deberá demostrar que el BYE:

- no genera eliminado;
- no genera serie competitiva;
- no admite score;
- no duplica avance;
- no corrompe standings;
- no crea rondas vacías;
- no duplica routing.

**Estado:** ✅ BASIC claro / ⚠️ paridad ADVANCED y tests pendientes.

# 29. Tres niveles de validez ADVANCED

## Validez estructural

Referencias y componentes correctos.

Respeta K, Q, capacidades, entradas, salidas y reglas.

- puede activar encuentros;
- no queda bloqueada;
- alcanza terminal.

# 32. Gates, slots y routing

P3 debe formalizar invariantes para el grafo interno.

## Gates

Auditar:

- capacidad;
- cantidad recibida;
- fuente;
- destino;
- overflow;
- underflow;
- duplicados;
- inaccesibilidad.

## Slots

Invariantes:

1. Un slot contiene como máximo un participante.
2. Un participante no ocupa posiciones incompatibles.
3. Una conexión no sobrescribe silenciosamente.
4. Un encuentro solo inicia cuando cumple su condición.
5. Debe poder explicarse el origen del participante.

## Routing

Debe comprobar:

- destino;
- orden;
- capacidad;
- rutas múltiples;
- activación;
- deduplicación;
- exits externos.

# 34. Standings — hallazgo de alta prioridad

Actualmente BASIC construye standings colocando:

1. supervivientes;
2. eliminados en orden inverso;
3. posiciones secuenciales.

Esto puede crear un orden artificial entre participantes eliminados en la misma ronda.

Ejemplo:

```text
Semifinalista A pierde primero
Semifinalista B pierde después
```

competitivamente ambos podrían ser:

```text
3.º–4.º
```

pero el orden de submit puede terminar dando:

```text
3.º
4.º
```

sin criterio real.

**Severidad: ALTA.**

P3.1 debe decidir:

- posiciones compartidas;
- placement por ronda;
- desempate opcional;
- tercer puesto explícito;
- diferencia entre placement y display order.

El engine rechaza resultados sobre matches completados y `MatchSeriesRuntime` también protege el estado de la serie.

- reenvío;
- refresh;
- resolución manual duplicada;
- selección duplicada.

Para Competition Lab, un segundo submit puede devolver un error claro; no es necesario construir idempotency keys de producción todavía.

# 50. Invariantes candidatas para P3.1

## I-01 Conservación

```text
initial
=
survivors/active
+
eliminated/finalized
```

sin pérdida ni duplicación.

## I-02 Unicidad

Un participante no ocupa dos posiciones incompatibles.

## I-03 Match terminado

No recibe otro resultado.

## I-04 BYE

No recibe score, no produce loser, no inicia serie y avanza una vez.

## I-05 Eliminación

Todo eliminado tiene causa competitiva.

## I-06 Superviviente

Todo superviviente proviene de una ruta válida.

## I-07 Serie

El engine recibe el resultado solo cuando la serie está resuelta.

## I-08 Decisión manual

Nada dependiente avanza mientras siga pendiente.

## I-09 Estructura vigente

Una estructura obsoleta no se ejecuta como vigente.

## I-10 Routing

Una emisión lógica no se duplica.

## I-11 Target

No se crean rondas después de alcanzar el objetivo.

## I-12 Standings

La posición no depende del orden accidental de submit.

Pero todavía no debe declararse Stable V1 porque:

1. El test directo del engine BASIC es placeholder.
2. Tests de runtime/routing revisados también son placeholders.
3. BASIC/ADVANCED no tienen una suite de paridad integral.
4. Standings necesita semántica formal.
5. RANDOM necesita contrato explícito.
6. STALE/VALID necesita política de ejecución formal.
7. Opciones avanzadas visibles deben demostrar ejecución real.
8. Tournament Graph necesita tests runtime de routing y deduplicación.

La conclusión de P3.0 es:

> **Single Elimination ya debe dejar de crecer horizontalmente y comenzar a estabilizarse verticalmente.**
