# 1. Propósito

P3.0 respondió:

> ¿Qué existe hoy y qué falta cerrar?

P3.1 responde una pregunta distinta:

> ¿Qué significa exactamente que Single Elimination sea correcto dentro de OmniMerge?

Este documento define el **contrato formal** que deberán respetar:

- formularios;
- Form Requests;
- Services;
- validadores;
- Preview;
- Competition Lab;
- runtime BASIC;
- runtime ADVANCED;
- Structure Graph;
- MatchSeriesRuntime;
- decisiones manuales;
- exits;
- Tournament Graph;
- tests.

A partir de P3.1 no será suficiente con que una funcionalidad “parezca funcionar”.

Para ser considerada parte de Stable V1 deberá satisfacer un contrato explícito.

---

# 2. Naturaleza normativa

Las palabras siguientes tienen significado obligatorio:

- **DEBE / MUST:** requisito obligatorio de Stable V1.
- **NO DEBE / MUST NOT:** comportamiento prohibido.
- **DEBERÍA / SHOULD:** comportamiento recomendado; cualquier excepción debe justificarse.
- **PUEDE / MAY:** comportamiento opcional permitido.
- **DIFERIDO:** fuera del alcance de P3.

Cuando este documento contradiga un comportamiento actual no protegido por un requisito anterior, **el contrato P3.1 será la referencia para las correcciones posteriores de P3**.

Esto no significa cambiar todo inmediatamente.

Significa que P3.2–P3.7 deberán llevar progresivamente el código hacia este contrato.

---

# 3. Principio central

Single Elimination Stable V1 debe cumplir:

```text
Configuration
    ↓
Validation
    ↓
Preview
    ↓
Preparation
    ↓
Runtime
    ↓

    ↓

    ↓
```

El sistema NO DEBE aceptar una configuración que:

```text
pueda guardarse
pero no pueda ejecutarse
```

sin explicarlo explícitamente al usuario.

---

# 4. Principio de verdad funcional

Se adopta como regla transversal:

> Una opción visible como disponible debe producir un efecto real, validable y testeable.

Por lo tanto:

```text
persistido ≠ soportado
```

y:

```text
aceptado por Rule::in ≠ ejecutable
```

Stable V1 distingue tres categorías:

| Categoría | Significado |
|---|---|
| SUPPORTED | Tiene semántica real, validación, runtime y tests. |
| CONDITIONALLY_SUPPORTED | Funciona únicamente bajo precondiciones explícitas. |
| NOT_SUPPORTED | Debe ocultarse, deshabilitarse o marcarse “Próximamente”. |

# 7. Vocabulario canónico

## 7.1. Participant

Competidor recibido por una fase.

Debe identificarse por un ID único dentro de la ejecución.

## 7.2. Seed

Posición competitiva inicial.

```text
seed = 1
```

es el seed más alto.

## 7.3. Round

Agrupación lógica de encuentros que comparten una etapa de progresión.

## 7.4. Encounter / Match

Unidad competitiva que recibe K participantes y produce Q clasificados.

## 7.5. Game

Unidad individual dentro de una serie.

```text
Match
 ├─ Game 1
 ├─ Game 2
 └─ ...
```

## 7.6. Series

Conjunto de Games cuyo resultado decide un Match.

## 7.7. Qualifier

Participante que avanza desde un Encounter.

## 7.8. Survivor

Participante que permanece clasificado cuando la fase termina.

## 7.9. Eliminated

Participante que deja de estar activo competitivamente en la fase.

## 7.10. BYE

Avance sin enfrentamiento competitivo.

Un BYE NO es una victoria obtenida contra un oponente.

## 7.11. Input Gate

Punto estructural de entrada de participantes.

## 7.12. Slot

Posición individual dentro de un Encounter.

## 7.13. Result

Salida interna de un Encounter.

## 7.14. Connection

Ruta que lleva participantes desde un Gate/Result hacia un Slot/Exit.

## 7.15. Exit

Salida externa de una fase.

## 7.16. Outcome

Resultado de fase publicado para consumo externo.

## 7.17. Placement

Posición o rango competitivo obtenido.

## 7.18. Elimination Event

Evento que registra dónde y cuándo un participante fue eliminado.

# 8. Modos de configuración

Solo existen dos modos canónicos:

```text
BASIC
ADVANCED
```

---

# 9. Contrato BASIC

BASIC representa:

> bracket de eliminación directa generado automáticamente por el motor.

BASIC DEBE:

- crear la topología;
- resolver BYEs;
- crear pairings;
- avanzar ganadores;
- eliminar perdedores;
- aplicar series;
- finalizar al objetivo configurado.

BASIC NO DEBE exigir al usuario editar:

- rounds internas;
- slots;
- results;
- connections.

---

# 10. Contrato ADVANCED

ADVANCED representa:

> Structure Graph explícito y previamente validado.

ADVANCED DEBE ejecutar la estructura persistida.

ADVANCED NO DEBE reconstruir silenciosamente una estructura diferente durante el runtime.

El runtime ADVANCED debe obedecer:

```text
Input Gates
    ↓
Connections
    ↓
Slots
    ↓
Encounters
    ↓
Results
    ↓
Connections
    ↓
Slots / Exits
```

---

# 11. Regla de separación BASIC / ADVANCED

Una misma configuración NO DEBE significar cosas contradictorias.

Los conceptos compartidos:

- participant;
- qualifier;
- survivor;
- eliminated;
- series;
- result;
- exit;
- completion;

DEBEN conservar el mismo significado.

La topología puede ser diferente.

La semántica competitiva no.

# 13. BASIC — contrato mínimo efectivo

Stable V1 BASIC se reduce formalmente a:

```text
POOL
+
AUTOMATIC routing
+
DUEL
+
2 → 1
```

El usuario puede seguir configurando:

- seeding;
- pairing;
- BYE assignment;
- reseeding;
- completion;
- series;
- round series rules.

Pero BASIC NO DEBE prometer estructuras avanzadas.

---

# 14. ADVANCED — soporte

ADVANCED utiliza el Structure Graph como fuente de verdad.

Por tanto, opciones como:

```text
input_mode
routing_mode
remainder_policy
```

pueden influir en la **generación** de la estructura.

Una vez que la estructura está validada, el runtime DEBE ejecutar la estructura resultante.

No debe recalcularla desde esos labels.

---

# 15. CUSTOM

P3.1 adopta esta decisión:

> Ninguna opción `CUSTOM` se considerará parte de Single Elimination Stable V1 mientras no exista un resolver ejecutable explícito.

Esto aplica a:

- `input_mode=CUSTOM`;
- `routing_mode=CUSTOM`;
- `encounter_profile=CUSTOM`.

La interfaz DEBE:

- deshabilitarla;
- ocultarla;
- o marcarla `Próximamente`.

---

# 16. Entrada de participantes

Todo `prepare()` recibe conceptualmente:

```text
participant_ids
participants metadata
```

El conjunto de IDs DEBE cumplir:

1. No estar vacío.
2. Cumplir el mínimo.
3. Cumplir el máximo.
4. Cumplir exact participants cuando exista.
5. Cumplir participant multiple cuando exista.
6. No contener duplicados.
7. Todos los IDs deben existir en `participants`.

---

# 17. Duplicados

P3.1 cambia una semántica importante.

Stable V1 NO DEBE corregir silenciosamente:

```text
[A, B, B, C]
```

a:

```text
[A, B, C]
```

Debe devolver error.

Motivo:

> Deduplicar silenciosamente puede esconder un error de routing anterior.

---

# 18. Participantes desconocidos

Si un ID no pertenece al Lab:

```text
P-999
```

el engine DEBE rechazar la preparación.

Nunca debe:

- ignorarlo;
- crear metadata implícita;
- sustituirlo;
- convertirlo en BYE.

---

# 19. Identidad

Durante una ejecución:

```text
participant_id
```

es la identidad competitiva.

La misma entidad no debe entrar dos veces con el mismo ID.

El soporte futuro de múltiples “instancias” de una misma entidad deberá utilizar IDs de inscripción diferentes en P8/P9.

---

# 20. Seeding — definición

Seeding determina el **orden competitivo inicial**.

Los modos Stable V1 son:

```text
INPUT_ORDER
RANKING
RANDOM
MANUAL
```

Todos deben producir un:

```text
seed_map
```

único:

```text
participant_id → integer seed
```

---

# 21. INPUT_ORDER

Contrato:

```text
input[0] → seed 1
input[1] → seed 2
...
```

INPUT_ORDER NO DEBE reordenar el input.

---

# 22. RANKING

RANKING DEBE requerir para cada participante:

```text
seed
```

como entero positivo.

Stable V1 DEBE rechazar:

- seed `null`;
- seed `0`;
- seed negativo;
- seed duplicado.

Los seeds pueden tener huecos si el dominio lo necesita:

```text
1, 4, 9, 20
```

pero el orden relativo debe ser inequívoco.

Para el bracket se normalizan a posiciones:

```text
1.º ranking → bracket seed 1
2.º ranking → bracket seed 2
...
```

---

# 23. RANDOM seeding

En Competition Lab Stable V1:

> RANDOM será determinista y reproducible.

La función debe depender de datos estables, como:

```text
phase identity
+
participant identity
+
random context version
```

Misma fase + mismos participantes + misma configuración:

```text
→ mismo orden
```

---

# 24. RANDOM no significa “reroll”

P3 NO implementará un botón de “nuevo sorteo”.

Si en el futuro se desea:

```text
Reroll
```

deberá existir un:

```text
random_seed
```

o:

```text
draw_id
```

explícito y persistido.

---

# 25. RANDOM en Tournament Runtime futuro

En P8:

```text
RANDOM
```

deberá ejecutarse una vez y persistirse como snapshot.

Por tanto:

```text
Lab:
    reproducible calculation

Real tournament:
    persisted draw
```

---

# 26. MANUAL seeding

MANUAL DEBE producir una permutación exacta.

Si los elegibles son:

```text
[A, B, C, D]
```

son válidos:

```text
[D, B, A, C]
```

No son válidos:

```text
[A, B, C]
[A, B, C, C]
[A, B, C, X]
```

---

# 27. Seed Map

Después de cualquier modo de seeding, el runtime DEBE guardar un mapa estable.

Ejemplo:

```json
{
  "A": 1,
  "D": 2,
  "B": 3,
  "C": 4
}
```

Este mapa es la referencia para:

- TOP_SEEDS;
- STANDARD_SEEDED;
- reseeding.

---

# 28. Pairing — definición

Pairing responde:

> Dado un conjunto ordenado de participantes, ¿quién enfrenta a quién?

Modos Stable V1:

```text
SEQUENTIAL
RANDOM
STANDARD_SEEDED
```

---

# 29. SEQUENTIAL

Contrato:

```text
[P1, P2, P3, P4, P5, P6]
```

produce:

```text
P1 vs P2
P3 vs P4
P5 vs P6
```

Si la cantidad no es compatible, la incompatibilidad debe haber sido resuelta antes mediante BYE o rechazo.

---

# 30. RANDOM pairing

RANDOM pairing DEBE:

1. producir un orden pseudoaleatorio reproducible en Lab;
2. formar pares consecutivos;
3. no repetir participantes;
4. no perder participantes.

La semántica de RANDOM pairing es distinta de RANDOM seeding.

Puede existir:

```text
seeding=RANKING
pairing=RANDOM
```

y eso es válido.

---

# 31. STANDARD_SEEDED — decisión crítica

P3.1 define:

> `STANDARD_SEEDED` significa bracket sembrado canónico donde los mejores seeds están distribuidos para encontrarse lo más tarde posible.

NO significa simplemente:

```text
1 vs N
2 vs N-1
3 vs N-2
...
```

colocados consecutivamente.

---

# 32. Ejemplo STANDARD_SEEDED — 8

Bracket correcto:

```text
Match 1: 1 vs 8
Match 2: 4 vs 5

Match 3: 2 vs 7
Match 4: 3 vs 6
```

Luego:

```text
M1 winner vs M2 winner
M3 winner vs M4 winner
```

Así:

```text
seed 1 y seed 2
```

solo pueden encontrarse en la final si ambos ganan.

---

# 33. Regla de distribución de seeds

Para una capacidad:

```text
N = potencia de 2
```

la distribución debe satisfacer:

- seed 1 y 2 en mitades opuestas;
- seeds 1–4 en cuartos diferentes;
- seeds 1–8 distribuidos en octavos apropiados;
- progresivamente.

La implementación puede usar un algoritmo recursivo de slot seeding.

---

# 34. Invariante STANDARD_SEEDED

Para todo:

```text
N = 2^k
```

los seeds:

```text
1 y 2
```

NO DEBEN poder enfrentarse antes de la final.

Los seeds:

```text
1..4
```

NO DEBEN compartir cuarto del bracket de forma que se enfrenten antes de semifinal cuando el tamaño lo permita.

---

# 35. Bracket fijo vs reseeding

Si:

```text
reseed_each_round = false
```

la ruta del bracket queda fijada en la ronda inicial.

Los ganadores avanzan por su rama.

No se reconstruyen pairings.

---

# 36. Reseeding

Si:

```text
reseed_each_round = true
```

Stable V1 define:

> después de cada ronda, los supervivientes se vuelven a ordenar por su seed original y se construyen nuevos pairings.

---

# 37. Compatibilidad de reseeding

Para Stable V1:

| Pairing | `reseed_each_round=true` |
|---|---|
| STANDARD_SEEDED | SUPPORTED |
| SEQUENTIAL | NOT_SUPPORTED |
| RANDOM | NOT_SUPPORTED |

Motivo:

- RANDOM ya define una nueva distribución;
- SEQUENTIAL con reseeding produce una semántica poco intuitiva;
- STANDARD_SEEDED tiene una interpretación competitiva clara.

Las combinaciones no soportadas DEBEN rechazarse o deshabilitarse.

---

# 38. STANDARD_SEEDED con reseeding

Con participantes:

```text
seed 1
seed 4
seed 6
seed 8
```

la siguiente ronda debe emparejar:

```text
1 vs 8
4 vs 6
```

siguiendo el criterio de extremos de los supervivientes reseedeados.

Aquí sí es correcto usar high-vs-low porque ya no se está creando el bracket inicial completo.

---

# 39. BYE — definición

BYE significa:

> avance automático sin disputar un encuentro competitivo contra otro participante.

Un BYE:

- no tiene rival real;
- no requiere Game;
- no requiere Series;
- no tiene score;
- no produce loser;
- no es una victoria competitiva.

---

# 40. Cantidad de BYEs BASIC

Para `N` participantes:

```text
bracket_capacity = next_power_of_two(N)
bye_count = bracket_capacity - N
```

Ejemplo:

```text
N = 5

capacity = 8
bye_count = 3
```

---

# 41. BYEs solo donde corresponden

En BASIC Stable V1 los BYEs automáticos se resuelven en la primera ronda necesaria para normalizar el bracket.

No se deben crear BYEs arbitrarios en rondas posteriores.

---

# 42. BYE y allow_byes

Si:

```text
N no es potencia de 2
```

y:

```text
allow_byes = false
```

BASIC DEBE rechazar la ejecución.

No debe inventar:

- preliminares;
- encuentros incompletos;
- participantes fantasma.

---

# 43. remainder_policy BASIC

Stable V1 BASIC soporta solamente:

```text
BYE
REJECT
```

Semántica:

### BYE

```text
irregular + allow_byes=true
→ normalizar con BYEs
```

### REJECT

```text
irregular
→ error
```

---

# 44. remainder_policy avanzadas

Estas políticas:

```text
PRELIMINARY
BALANCED
INCOMPLETE_MATCH
MANUAL
```

NO son políticas dinámicas del runtime BASIC.

En ADVANCED pueden existir como políticas del generador solamente cuando:

- el generador produzca estructura real;
- el validator la acepte;
- la estructura sea executable;
- exista test.

---

# 45. TOP_SEEDS BYE

TOP_SEEDS asigna BYE a los mejores seeds.

Si se necesitan:

```text
B
```

BYEs, reciben BYE:

```text
seed 1 ... seed B
```

---

# 46. BYE dentro del bracket sembrado

P3.1 fija una regla importante:

> Un BYE debe formar parte de la topología del bracket, no añadirse como una lista separada que altere la distribución de seeds.

Ejemplo:

```text
5 participantes
capacidad 8
3 BYEs
```

Los tres BYEs deben ocupar slots que preserven el bracket seeded.

---

# 47. RANDOM BYE

RANDOM BYE:

- selecciona exactamente `bye_count`;
- es reproducible en Lab;
- no puede seleccionar dos veces el mismo participante.

---

# 48. MANUAL BYE

MANUAL BYE requiere exactamente:

```text
bye_count
```

IDs únicos.

Cualquier cantidad distinta es error.

---

# 49. BYE y series

Un BYE NO crea:

```text
runtime.series[match_id]
```

y no consume Games.

---

# 50. BYE y métricas

Cualquier métrica denominada:

```text
matches played
games played
wins
losses
```

NO DEBE contar un BYE como un encuentro disputado.

Puede existir una métrica independiente:

```text
bye_count
```

---

# 51. Match estructural vs match disputado

Si por compatibilidad interna existe un nodo de match para representar BYE:

```text
status=BYE
```

puede formar parte de la topología.

Pero la UI NO DEBE mostrarlo como partido jugado.

---

# 52. Completion Mode

Modos:

```text
WINNER
SURVIVORS
```

---

# 53. WINNER

Contrato:

```text
target_survivors = 1
```

Siempre.

La UI no necesita pedir `target_survivors` cuando se usa WINNER.

---

# 54. SURVIVORS

SURVIVORS finaliza cuando quedan exactamente:

```text
target_survivors
```

participantes activos.

---

# 55. Target BASIC

En BASIC:

```text
target_survivors
```

DEBE ser potencia de dos.

Además:

```text
1 <= target < N
```

---

# 56. Exactitud del target

BASIC DEBE terminar cuando:

```text
count(survivors) == target_survivors
```

No debe utilizar una finalización silenciosa por:

```text
count(survivors) < target
```

Si ocurre un overshoot:

```text
survivors < target
```

debe considerarse error de integridad.

---

# 57. SURVIVORS no significa ranking

Si una fase termina con:

```text
4 supervivientes
```

y esos cuatro no se enfrentaron para ordenarse, NO DEBE inventarse:

```text
1.º
2.º
3.º
4.º
```

El resultado correcto es:

```text
clasificados / supervivientes no ordenados
```

salvo que exista un criterio explícito.

---

# 58. Estados globales del runtime

Los estados canónicos de fase son:

```text
AWAITING_DECISION
RUNNING
COMPLETED
```

Los errores de preparación NO crean un estado `ERROR`.

Se devuelven como validación y no se inicia ejecución válida.

---

# 59. AWAITING_DECISION

Significa:

> no puede comenzar o continuar una transición porque falta una decisión humana soportada.

Mientras esté activo:

- no se crean nuevos encuentros dependientes;
- no se completan outcomes;
- no se consume la decisión dos veces.

---

# 60. RUNNING

Significa:

> existe trabajo competitivo pendiente o rutas pendientes de resolución automática.

---

# 61. COMPLETED

Significa:

> el contrato terminal de la fase fue satisfecho y no existen dependencias competitivas requeridas sin resolver.

Una fase COMPLETED:

- no acepta nuevos scores;
- no acepta nuevas selections;
- no acepta decisiones antiguas.

---

# 62. Estados de Round

BASIC:

```text
RUNNING
COMPLETED
```

ADVANCED:

```text
WAITING
RUNNING
COMPLETED
```

---

# 63. WAITING Round

Una Round ADVANCED está WAITING cuando:

- contiene encuentros;
- ninguno está listo;
- espera participantes de rutas anteriores.

---

# 64. Estados de Match

BASIC:

```text
PENDING
BYE
COMPLETED
```

ADVANCED:

```text
WAITING
PENDING
COMPLETED
```

BYE avanzado será una transición estructural automática, no un match disputable.

---

# 65. WAITING Match

Significa:

> todavía no recibió todos los participantes requeridos.

No acepta:

- score;
- selection;
- serie.

---

# 66. PENDING Match

Significa:

> tiene todos los participantes necesarios y está listo para resolución.

---

# 67. COMPLETED Match

Tiene una resolución definitiva.

No acepta otra.

---

# 68. Series — alcance

Stable V1 soporta series A/B únicamente para:

```text
DUEL
2 → 1
```

Los encuentros K > 2 se resuelven mediante selección ordenada de clasificados.

No utilizan `MatchSeriesRuntime` hasta que exista una abstracción multi-party.

---

# 69. BEST_OF

Valores soportados:

```text
1
3
5
7
9
```

El número es siempre impar.

---

# 70. BEST_OF — condición de finalización

Para:

```text
BO(n)
```

se requiere:

```text
wins_required = floor(n / 2) + 1
```

La serie termina inmediatamente al alcanzarse.

---

# 71. BO3

```text
2-0 → termina
2-1 → termina
1-0 → continúa
1-1 → continúa
```

No se disputan juegos innecesarios después de obtener mayoría.

---

# 72. Juegos empatados

Para Single Elimination Stable V1:

> cada Game de una serie DUEL debe producir un ganador.

Por tanto:

```text
score_a == score_b
```

es error.

---

# 73. Score

Todo score DEBE ser:

```text
integer >= 0
```

No se admiten negativos.

---

# 74. FIXED_GAMES

FIXED_GAMES significa:

> disputar obligatoriamente la cantidad nominal configurada de Games.

Ejemplo:

```text
FIXED_GAMES=5
```

debe disputar los cinco, incluso si A ya ganó los tres primeros.

---

# 75. FIXED_GAMES empatado

Si al completar la cantidad nominal existe empate en Games ganados:

```text
2-2
3-3
```

Single Elimination necesita un ganador.

P3.1 adopta:

> sudden death adicional.

Se juegan Games extra hasta que las victorias acumuladas dejen de estar empatadas después de la cantidad nominal.

---

# 76. Tiebreak required

El runtime debe exponer:

```text
tiebreak_required=true
```

mientras se encuentra en esa situación.

La UI DEBE explicar:

> La cantidad fija ya se completó, pero la serie necesita un desempate.

---

# 77. Resultado del engine

Para BO1, el score final del Match puede conservar el score del Game.

Para BO3+ y FIXED_GAMES, el resultado competitivo debe distinguir:

```text
game score
```

de:

```text
series score
```

Ejemplo:

```text
Game 1: 10-8
Game 2: 4-7
Game 3: 3-1

Series: 2-1
```

---

# 78. Regla de series por ronda

Una regla específica de ronda sobrescribe la configuración por defecto.

Precedencia:

```text
Round rule
    >
Default phase series
```

---

# 79. participants_in_round — decisión

P3.1 define:

> `participants_in_round` representa la capacidad competitiva nominal de la ronda del bracket.

No representa únicamente:

```text
participantes que disputan partido
```

después de quitar BYEs.

Ejemplo:

```text
5 participantes
capacidad inicial = 8
```

la primera ronda se considera:

```text
participants_in_round = 8
```

para seleccionar su regla de serie.

---

# 80. Motivación

Esto permite que:

```text
Regla para ronda de 8
```

siga aplicando a un bracket de capacidad 8 aunque existan BYEs.

---

# 81. Decisiones manuales

Single Elimination Stable V1 soporta manual decisions para:

- orden/seeding manual BASIC;
- selección de BYEs BASIC;
- selección ordenada K → Q ADVANCED cuando el usuario resuelve manualmente.

---

# 82. Estado manual

Toda decisión debe contener:

```text
decision_id
scope
type
eligible_participant_ids
constraints
```

---

# 83. decision_id

El `decision_id` identifica el estado exacto que se está resolviendo.

Un payload con un `decision_id` anterior DEBE rechazarse.

---

# 84. Permutación manual

Cuando una decisión exige orden:

```text
ordered_participant_ids
```

DEBE ser una permutación exacta.

No se deduplica silenciosamente.

---

# 85. Selección manual

Cuando exige:

```text
Q clasificados
```

el payload debe contener exactamente Q IDs únicos.

---

# 86. Resolución única

Una decisión resuelta no puede resolverse de nuevo.

---

# 87. K → Q

ADVANCED soporta:

```text
K entrants
→
Q qualifiers
```

sujeto a:

```text
K >= 2
1 <= Q < K
```

---

# 88. DUEL

DUEL significa exactamente:

```text
K=2
Q=1
```

---

# 89. MULTI_COMPETITOR

MULTI_COMPETITOR exige:

```text
K >= 3
```

y:

```text
1 <= Q < K
```

---

# 90. Resolución de MULTI_COMPETITOR

Stable V1 usa:

```text
ordered qualifier selection
```

No score A/B.

---

# 91. qualifier_ids ordenados

P3.1 fija:

> El orden de `qualifier_ids` es semánticamente significativo.

Ejemplo:

```json
["P3", "P1"]
```

significa:

```text
posición clasificatoria 1 → P3
posición clasificatoria 2 → P1
```

---

# 92. Duplicados en qualifier_ids

Payload:

```text
[A, A]
```

es error.

NO debe convertirse automáticamente en:

```text
[A]
```

---

# 93. Qualifier ajeno

Todo qualifier debe pertenecer al Encounter actual.

De lo contrario:

```text
error
```

---

# 94. Eliminated set en K → Q

Después de resolver:

```text
eliminated =
participants
-
qualifiers
```

Exactamente.

---

# 95. Conservación local

Para todo Encounter:

```text
K
=
Q qualifiers
+
(K-Q) eliminated
```

sin duplicados.

---

# 96. Structure Graph — fuente de verdad

En ADVANCED, la estructura activa es la fuente de verdad runtime.

El engine NO DEBE derivar conexiones nuevas durante la ejecución.

---

# 97. Estados persistentes de estructura

P3.1 define los estados:

```text
NOT_GENERATED
GENERATED
VALID
INVALID
STALE
BLOCKED
```

`BLOCKED` es una extensión normativa propuesta para P3.4.

---

# 98. NOT_GENERATED

No existe estructura ejecutable.

---

# 99. GENERATED

Existe estructura recién creada o modificada que todavía no ha completado el ciclo de validación persistida.

---

# 100. VALID

P3.1 redefine formalmente `VALID`.

Solo puede significar:

```text
validation.valid == true
AND
validation.executable == true
AND
fingerprint current == stored fingerprint
```

---

# 101. INVALID

Existe al menos un error estructural o contractual.

---

# 102. STALE

La estructura fue construida/validada contra una configuración anterior.

No puede ejecutarse.

---

# 103. BLOCKED

La estructura puede ser sintácticamente válida pero necesita una capacidad no ejecutable por Stable V1.

Ejemplos:

- manual routing no soportado;
- custom input;
- custom encounter;
- manual connection sin resolver.

---

# 104. VALID no puede significar BLOCKED

La UI no debe mostrar:

```text
Lista para probar
```

si:

```text
validation.executable == false
```

---

# 105. Gate de ejecución ADVANCED

Competition Lab solo puede preparar ADVANCED cuando:

```text
structure_status == VALID
AND
validator.valid == true
AND
validator.executable == true
AND
fingerprint vigente
```

---

# 106. Existencia de rounds no es suficiente

La condición:

```text
hay rounds ACTIVE
```

NO es suficiente para ejecutar ADVANCED.

---

# 107. Fingerprint — objetivo

`structure_fingerprint` debe permitir detectar modificaciones que invaliden el contrato ejecutable.

---

# 108. Fingerprint — payload canónico

Debe derivarse de datos normalizados de ejecución, como mínimo:

```text
Phase participant contract
Single Elimination settings relevantes
Round rules
Input gates activos
Rounds activos
Encounters activos
Slots activos
Results activos
Connections activas
Exits relevantes
```

---

# 109. Fingerprint determinista

La serialización debe:

- ordenar claves;
- ordenar colecciones por ID/posición estable;
- eliminar timestamps no competitivos;
- producir el mismo hash para estructuras equivalentes.

---

# 110. Cambio de configuración

Si cambia un campo que afecta ejecución:

```text
structure_status → STALE
```

y:

```text
structure_validated_at → null
```

---

# 111. Campos que invalidan estructura

Como mínimo:

- input mode;
- routing mode;
- K;
- Q;
- encounter profile;
- remainder policy;
- completion target;
- seeding cuando afecta slots generados;
- pairing;
- BYE policy;
- reseeding;
- series cuando se copia a encounters;
- round rules;
- participant contract.

---

# 112. Validación ADVANCED en tres niveles

Stable V1 distingue:

```text
STRUCTURAL_VALIDITY
CONTRACT_VALIDITY
LIVENESS
```

---

# 113. Structural Validity

Comprueba:

- referencias;
- IDs;
- slots;
- connections;
- gates;
- results;
- exits;
- direcciones.

---

# 114. Contract Validity

Comprueba:

- K;
- Q;
- capacidades;
- posiciones;
- reglas;
- cantidad de outputs;
- restricciones de fase.

---

# 115. Liveness

Comprueba:

> ¿Puede esta estructura comenzar y llegar a un estado terminal?

Debe detectar:

- encuentro inaccesible;
- dependencia imposible;
- ruta sin fuente;
- slot requerido imposible de llenar;
- deadlock.

---

# 116. Warnings

Un warning puede no invalidar estructura.

Pero si exige una capacidad que el runtime no soporta:

```text
executable = false
```

y:

```text
structure_status = BLOCKED
```

---

# 117. Input Gates

Todo Gate activo debe tener un contrato de capacidad coherente.

Debe cumplirse:

```text
min <= exact <= max
```

cuando existan esos campos.

---

# 118. Gate requerido

Un Gate requerido debe tener al menos un destino competitivo válido.

---

# 119. Entrada exacta

Si:

```text
exact_participants = X
```

debe recibir exactamente X.

Ni X-1 ni X+1.

---

# 120. Participantes sobrantes

Después de distribuir los participantes iniciales entre Gates:

```text
remaining == []
```

Debe ser obligatorio.

---

# 121. Slot

Un Slot puede contener como máximo un participante.

---

# 122. Slot overwrite

Intentar colocar otro participante en un Slot ocupado debe ser error.

Nunca:

```text
último gana
```

---

# 123. Slot requerido

Un Encounter no puede pasar a PENDING si falta un Slot requerido.

---

# 124. Capacidad del Encounter

Un Encounter pasa a PENDING cuando ha recibido exactamente la cantidad requerida para su modo de resolución.

---

# 125. ADVANCED BYE

En ADVANCED un BYE debe estar representado por la estructura como una transición automática.

No debe pedir al usuario un score contra `null`.

---

# 126. ADVANCED BYE — resolución

La estructura/generator debe expresar:

```text
participant
→ automatic advance
```

mediante un mecanismo ejecutable.

P3.4 deberá asegurar que el runtime lo resuelva automáticamente.

---

# 127. Connection

Una Connection debe tener:

```text
source
target
allocation semantics
priority
status
```

---

# 128. Allocation modes

Stable V1 reconoce las semánticas ya presentes:

```text
POSITION
TAKE_N
REMAINDER
```

Toda otra modalidad debe estar explícitamente soportada.

---

# 129. POSITION

Selecciona exactamente la posición indicada del conjunto ordenado de la fuente.

La posición comienza en:

```text
1
```

---

# 130. TAKE_N

Consume los siguientes N participantes disponibles de la fuente.

---

# 131. REMAINDER

Consume el resto de participantes todavía no consumidos por conexiones anteriores compatibles.

---

# 132. Priority

Cuando varias connections consumen una misma fuente con modos secuenciales:

```text
priority
```

determina el orden.

---

# 133. Connection sin selección

Si una conexión POSITION apunta a una posición inexistente, la validación debería detectarlo si es estáticamente posible.

Durante runtime, no debe inventar participante.

---

# 134. Fan-out

P3.1 adopta una política conservadora:

> Una misma posición competitiva no puede alimentar dos destinos competitivos internos diferentes salvo que el dominio marque explícitamente la conexión como fan-out.

Como actualmente no existe un contrato formal de `fan_out`, Stable V1 debe considerar la duplicación competitiva como inválida.

---

# 135. Outputs descriptivos

La misma persona puede conceptualmente pertenecer a categorías solapadas:

```text
Champion
TOP 2
Survivors
```

pero esto pertenece a **clasificación de outcomes**, no a duplicar físicamente al participante en dos Slots competitivos.

---

# 136. Result

Un Result representa una salida ordenada de un Encounter.

Debe definir:

- status competitivo;
- rango/posición;
- quantity.

---

# 137. ACTIVE Result

Un Result con participant status ACTIVE consume qualifiers.

---

# 138. ELIMINATED Result

Un Result ELIMINATED consume non-qualifiers.

---

# 139. Orden de Results

Si un Result necesita:

```text
posición 1
posición 2
```

el Encounter debe haber producido qualifiers ordenados.

---

# 140. Eliminación — definición

Un participante queda ELIMINATED cuando un Encounter resuelto determina que no forma parte de sus qualifiers.

---

# 141. BYE no elimina

Un BYE no produce eliminated participant.

---

# 142. Elimination Event

Toda eliminación DEBE crear conceptualmente un registro runtime:

```json
{
  "participant_id": "...",
  "round_number": 2,
  "match_id": "...",
  "source": "MATCH_RESULT"
}
```

---

# 143. Propósito del Elimination Event

Permite:

- standings;
- eliminated-by-round;
- ON_ELIMINATION;
- exits;
- debugging;
- futura persistencia P8.

---

# 144. Unicidad de eliminación

Cada participante puede tener como máximo un evento de eliminación terminal dentro de la misma ejecución de fase.

---

# 145. elimination sequence

El runtime puede guardar un `sequence` técnico.

Pero ese sequence NO determina placement competitivo.

---

# 146. Standings — principio

P3.1 adopta:

> La posición competitiva no puede depender del orden accidental en que el usuario envía resultados.

---

# 147. Placement bands

Los participantes eliminados en la misma etapa competitiva comparten un rango.

Ejemplo de 8 participantes hasta ganador:

```text
Champion             → 1
Final loser          → 2
Semifinal losers     → 3–4
Quarterfinal losers  → 5–8
```

---

# 148. Modelo de placement recomendado

Cada standing debería poder expresar:

```text
position_from
position_to
```

Ejemplos:

```json
{
  "participant_id": "P1",
  "position_from": 1,
  "position_to": 1
}
```

```json
{
  "participant_id": "P4",
  "position_from": 3,
  "position_to": 4
}
```

---

# 149. Compatibilidad de `position`

Si consumidores existentes necesitan:

```text
position
```

puede conservarse temporalmente:

```text
position = position_from
```

pero la UI debe mostrar rango cuando:

```text
position_from != position_to
```

---

# 150. Survivor placement

Si `completion_mode=WINNER`:

```text
winner → 1
```

---

# 151. Survivor placement en SURVIVORS

Si la fase termina con Q supervivientes sin ordenarlos entre sí:

```text
position_from = 1
position_to = Q
status = SURVIVOR
placement_status = UNRANKED_SURVIVOR
```

Todos comparten la banda.

---

# 152. No inventar orden de supervivientes

Si:

```text
target_survivors = 4
```

NO se asigna automáticamente:

```text
1, 2, 3, 4
```

---

# 153. Runner-up

Existe runner-up únicamente si se disputó una final 2 → 1.

Si la fase termina en 2 supervivientes:

```text
no hay runner-up
```

porque ambos son clasificados.

---

# 154. Tercer puesto

Single Elimination básico NO inventa tercer puesto.

Sin match específico:

```text
semifinal losers → 3–4
```

---

# 155. Third-place match ADVANCED

Si la estructura contiene un Encounter específico por tercer puesto:

- ganador → 3;
- perdedor → 4.

Es válido.

---

# 156. Placement por ronda

La banda de una eliminación se calcula por la cantidad de participantes que permanecen después de la etapa, no por timestamp.

---

# 157. Ejemplo 16

```text
Champion       1
Runner-up      2
SF losers      3–4
QF losers      5–8
R16 losers     9–16
```

---

# 158. Eliminaciones con BYE

Un participante que obtiene BYE y pierde después se clasifica según la ronda en que realmente fue eliminado.

El BYE no crea una ronda de eliminación ficticia.

---

# 159. Exits

Un Exit es una salida externa con semántica definida.

No debe depender de “el índice actual del array” sin un selector explícito.

---

# 160. Selectores de exit Stable V1

P3 deberá soportar como mínimo:

```text
SURVIVORS
WINNER
RUNNER_UP
ELIMINATED
ELIMINATED_IN_ROUND
TOP_N
POSITION
```

cuando el modelo actual permita representarlos.

---

# 161. WINNER Exit

Solo produce un participante cuando existe un ganador único.

---

# 162. RUNNER_UP Exit

Solo existe si hubo final competitiva 2 → 1.

---

# 163. SURVIVORS Exit

Produce todos los supervivientes terminales.

---

# 164. ELIMINATED Exit

Puede representar todos los eliminados.

Su orden no debe utilizarse como ranking si no existe criterio.

---

# 165. ELIMINATED_IN_ROUND

Debe usar `Elimination Event.round_number`.

No debe inferirse por orden de submit.

---

# 166. TOP_N

TOP_N solo puede utilizarse si existen placements suficientemente definidos.

Si una frontera corta una banda empatada:

```text
TOP 3
```

pero existe:

```text
3–4
```

el sistema NO debe escoger arbitrariamente uno.

---

# 167. TOP_N y empate de placement

Stable V1 debe tratar el caso como:

```text
ambiguous cut
```

y requerir:

- regla explícita;
- match de desempate;
- o no permitir ese selector.

No usar RANDOM silencioso.

---

# 168. POSITION

POSITION `3` solo puede devolver un participante si el tercer lugar es único.

Si la banda es:

```text
3–4
```

POSITION 3 es ambiguo.

---

# 169. ON_ELIMINATION

ON_ELIMINATION representa un evento durante ejecución.

Debe dispararse cuando la eliminación se vuelve definitiva.

No necesita esperar a `phase COMPLETED`.

---

# 170. Evento único

Para:

```text
participant P
match M
```

ON_ELIMINATION se emite una sola vez.

---

# 171. Ledger de emisiones

El runtime DEBE disponer conceptualmente de una forma de recordar:

```text
qué eventos ya fueron emitidos
```

Ejemplo:

```text
emitted_events
```

o una estructura equivalente.

---

# 172. Clave de deduplicación

Puede definirse:

```text
ELIMINATION:{match_id}:{participant_id}
```

para Lab.

P8 podrá utilizar IDs persistentes.

---

# 173. Outcomes

`outcomes` representa la vista externa de exits ya resueltos.

Debe ser derivable de:

```text
exit definitions
+
runtime facts
```

---

# 174. Outcome no modifica competencia

Construir outcomes NO DEBE:

- eliminar;
- clasificar;
- duplicar slots;
- cambiar winner.

Solo publica información ya determinada.

---

# 175. Tournament Graph

Tournament Graph consume outputs de la fase.

El motor Single Elimination NO DEBE conocer detalles de la siguiente fase.

Debe producir outcomes/eventos y el router externo decide destinos.

---

# 176. Separación de responsabilidades

```text
Single Elimination
    determina resultado competitivo

Tournament Graph
    determina destino externo
```

---

# 177. Integridad de routing

Un participante enviado a una siguiente fase debe provenir de un outcome válido.

Nunca de un array auxiliar no contractual.

---

# 178. Paridad Preview / Runtime

Stable V1 exige:

> Toda decisión determinista visible en Preview debe coincidir con Runtime.

---

# 179. Paridad estructural BASIC

Para misma configuración + participantes:

Preview y Runtime deben coincidir en:

- bracket capacity;
- bye count;
- round count;
- target;
- pairing semantics;
- series por ronda.

---

# 180. RANDOM y parity

Como RANDOM es determinista en Lab:

Preview y Runtime DEBERÍAN producir el mismo draw cuando ambos poseen los mismos IDs.

---

# 181. ADVANCED parity

El visualizador debe representar exactamente:

- rounds;
- encounters;
- slots;
- connections;
- exits;

que ejecutará GraphRuntime.

---

# 182. Visualizer no inventa

El visualizador NO DEBE mostrar una conexión que no exista en runtime.

---

# 183. Runtime no inventa

GraphRuntime NO DEBE añadir rutas invisibles para “hacer que funcione”.

---

# 184. Validación antes de runtime

Orden obligatorio:

```text

        ↓
validate configuration

validate structure if ADVANCED

        ↓
prepare runtime
```

# 194. Invariante global I-01 — identidad única

```text
count(participant_ids)
==
count(unique(participant_ids))
```

Siempre.

# 195. I-02 — existencia

En Single Elimination no se crean participantes nuevos.

# 196. I-03 — conservación

```text
=
Terminal Survivors
∪
Terminal Eliminated
```

y ambos conjuntos son disjuntos.

---

# 197. I-04 — exclusividad

Nadie puede estar simultáneamente:

```text
SURVIVOR
AND
ELIMINATED
```

---

# 198. I-05 — eliminación única

Cada participante se elimina como máximo una vez.

---

# 199. I-06 — BYE

BYE:

```text
winner = único participante
loser = null
score = null
series = none
```

---

# 200. I-07 — Match completo

Un Match COMPLETED es inmutable dentro de la ejecución del Lab.

---

# 201. I-08 — Series

Un Match con serie solo se completa cuando `MatchSeriesRuntime` declara `completed=true`.

---

# 202. I-09 — target

BASIC completa con exactamente Q supervivientes.

# 231. BASIC — algoritmo conceptual

```text
1. validate participants
2. resolve manual preparation if required
3. produce seed map
4. calculate bracket capacity
5. determine BYEs
6. build bracket topology
7. apply first-round BYEs
8. expose playable matches
9. resolve series
10. record winners/losers
11. emit eliminations
12. if target reached -> complete
13. otherwise advance bracket/reseed if configured
14. repeat
```

# 359. Riesgos de implementación

## R-01 — Cambio de STANDARD_SEEDED

- tests;
- preview parity;
- documentar cambio;
- considerar estructuras BASIC como regenerables.

# 360. R-02 — Strict duplicates

Puede revelar routing previo defectuoso.

Eso es deseable.

No volver a deduplicar silenciosamente.

---

# 361. R-03 — Strict RANKING

Configuraciones que antes toleraban seeds faltantes podrán fallar.

La UI deberá validar previamente.

---

Mantener `position` temporalmente como compatibilidad.

---

# 363. R-05 — Structure BLOCKED

Agregar un estado nuevo requiere revisar:

- model label;
- Blade badges;
- controller;
- service;
- tests.

---

# 364. R-06 — Fingerprint

Debe evitar marcar STALE por cambios cosméticos.

Por eso el payload debe incluir solo datos competitivos.

---

# 365. R-07 — Advanced deadlock

Un detector demasiado agresivo podría marcar como deadlock algo que espera una transición manual soportada.

Distinguir:

```text
AWAITING_DECISION
```

de:

```text
WAITING imposible
```

---

# 366. R-08 — Exit overlap

Outcomes descriptivos pueden solaparse.

No confundir solapamiento informativo con duplicación competitiva en Slots.
