# P3.6 — UX, Estados, Errores y Confirmaciones
## Plan de implementación incremental y estabilización

**Proyecto:** OmniMerge  
**Área:** Torneos → Single Elimination  
**Etapa:** P3 — Cierre de Single Elimination como motor de referencia estable  
**Subetapa:** P3.6 — UX, estados, errores, confirmaciones y claridad operativa  
**Documento:** Plan incremental P3.6.1–P3.6.8  
**Baseline documental:** posterior a P3.5  
**Objetivo de cierre:** preparar Single Elimination para P3.7 (tests finales) sin introducir regresiones de interfaz.

---

# 1. Propósito de P3.6

P3.6 no tiene como objetivo volver a diseñar el motor competitivo de Single Elimination.

Las reglas competitivas principales ya fueron cerradas progresivamente en:

- P3.2 — Runtime BASIC.
- P3.3 — Series y resultados.
- P3.4 — ADVANCED / Structure Graph.
- P3.5 — Results, Exits y emisiones hacia Tournament Graph.

P3.6 se concentra en la capa que permite que todo ese comportamiento sea **comprensible, visible, predecible y seguro para el usuario**.

La meta es que OmniMerge nunca presente una capacidad como funcional si todavía no lo es, que los errores sean accionables, que los estados internos tengan una representación visual clara y que las acciones destructivas o que implican pérdida de trabajo requieran una confirmación consistente con la interfaz del proyecto.

En términos simples:

> P3.2–P3.5 cerraron principalmente el comportamiento del motor.  
> P3.6 debe cerrar cómo ese comportamiento se comunica y se opera desde la interfaz.

---

# 2. Por qué P3.6 se divide en partes

La primera aproximación a P3.6 agrupaba demasiados cambios dentro de un único patch:

- sistema global de confirmaciones;
- cambios sin guardar;
- formularios;
- Preview;
- Structure Graph;
- diagnósticos;
- I/O;
- Competition Lab;
- BYEs;
- Series;
- standings;
- decisiones manuales;
- estados de Tournament Graph.

Ese enfoque dificultaba aislar regresiones.

Una modificación en JavaScript podía afectar indirectamente varios componentes Blade que usaban `x-show`, `x-text`, `x-cloak` o métodos Alpine nuevos. Cuando una de esas dependencias fallaba, la consecuencia visual no siempre era un error evidente: podían desaparecer secciones, quedar mensajes vacíos o mostrarse solo una parte de la interfaz.

Por esa razón, P3.6 se reorganiza en **ocho entregas pequeñas y secuenciales**.

Cada parte debe cumplir cuatro condiciones antes de avanzar:

1. El patch aplica sobre el commit inmediatamente anterior.
2. La interfaz afectada se revisa manualmente.
3. El build y las pruebas correspondientes pasan.
4. Solo después se crea el commit y se continúa.

La nueva regla de trabajo será:

```text
P3.6.n
↓
aplicar patch
↓
build
↓
pruebas automáticas
↓
pruebas manuales
↓
commit
↓
subir
↓
usar ese commit como baseline de P3.6.n+1
```

Nunca se debe generar P3.6.4, por ejemplo, suponiendo todavía el estado de P3.5 si P3.6.1–P3.6.3 ya fueron incorporados.

# 3. Principios de implementación de P3.6

## 3.1. UX veraz

Una opción no implementada no debe parecer utilizable.

Estados posibles:

- **Disponible**
- **Requiere modo avanzado**
- **Próximamente**
- **No compatible**
- **Bloqueado por configuración**
- **Pendiente de validación**

No se debe usar lenguaje ambiguo como:

> “Requiere constructor”

si realmente Stable V1 todavía no puede ejecutar esa capacidad.

---

## 3.2. No duplicar reglas competitivas en JavaScript

El frontend debe representar lo que informa el backend/runtime.

Ejemplo:

Si el runtime ya devuelve:

```text
position_from
position_to
series_format
game_wins_a
game_wins_b
next_game_number
tiebreak_required
status
```

la interfaz debe usar esos datos.

No debe recalcular de forma independiente quién es campeón, cuántas partidas faltan o qué posición corresponde.

---

## 3.3. Blade debe ser resistente

Se evitará introducir una gran cantidad de helpers Alpine nuevos únicamente para que la vista pueda renderizar.

La preferencia será:

1. usar datos ya existentes;
2. usar helpers ya existentes;
3. añadir helpers nuevos solo cuando aporten comportamiento real;
4. evitar que un bloque completo dependa de un helper nuevo si puede expresarse directamente con el estado existente.

El objetivo es reducir escenarios donde un bundle JavaScript desactualizado provoque:

- tarjetas vacías;
- elementos ocultos;
- errores Alpine;
- mensajes que no aparecen;
- `x-cloak` que nunca se libera.

---

## 3.4. Cada pantalla tiene una responsabilidad

P3.6 no debe crear un sistema global excesivamente intrusivo.

Por ejemplo:

- confirmaciones globales → `OmniConfirm`;
- dirty state de Single Elimination → workspace de Single Elimination;
- runtime del Lab → Competition Lab;
- Structure status → Structure UI;
- Exit timing → I/O Manager.

Esto evita que una mejora local afecte Dashboard, Biblioteca, Entidades u otros módulos.

---

## 3.5. El navegador conserva las responsabilidades que le pertenecen

OmniMerge puede usar su modal propio para:

- borrar;
- descartar;
- resetear;
- abandonar una pantalla mediante navegación interna;
- cerrar un Lab temporal.

Pero para:

- F5;
- cerrar pestaña;
- cerrar navegador;
- navegación externa forzada;

el mecanismo de último recurso seguirá siendo `beforeunload`.

Los navegadores modernos no permiten reemplazar de forma fiable ese diálogo por un modal completamente personalizado.

---

# 5. P3.6.1 — OmniConfirm estable

## 5.1. Objetivo

Convertir el sistema existente de confirmaciones de OmniMerge en una base estable que pueda utilizarse tanto desde formularios como desde acciones JavaScript.

Actualmente OmniMerge ya dispone de un modal propio para formularios con:

```html
<form data-omni-confirm>
```

P3.6.1 ampliará esa capacidad sin introducir un segundo modal.

---

## 5.2. Qué se hará

Se mantendrá el componente visual existente:

```text
resources/views/components/omni-confirm-modal.blade.php
```

y el controlador global:

```text
resources/js/app.js
```

Se incorporará una API programática segura conceptualmente equivalente a:

```js
const accepted = await window.OmniConfirm.request({
    title: 'Confirmar acción',
    message: '¿Deseas continuar?',
    detail: 'Esta acción no puede deshacerse.',
    actionLabel: 'Continuar',
    cancelLabel: 'Cancelar',
    variant: 'danger',
});

if (!accepted) {
    return;
}
```

La implementación exacta deberá integrarse con el mismo modal existente.

---

## 5.3. Qué NO se hará todavía

P3.6.1 no modificará:

- Competition Lab;
- dirty navigation;
- Single Elimination settings;
- Structure Graph;
- Series;
- standings;
- decisiones manuales.

El objetivo es probar únicamente la infraestructura de confirmación.

---

## 5.4. Comportamientos requeridos

El modal debe:

- abrir correctamente;
- cerrar con Cancelar;
- cerrar mediante Escape;
- cerrar mediante backdrop cuando corresponda;
- bloquear scroll;
- devolver foco de forma razonable;
- impedir doble confirmación;
- seguir funcionando con formularios Laravel;
- seguir respetando CSRF;
- seguir respetando `_method`;
- no utilizar `window.confirm()`.

---

## 5.5. Definition of Done

P3.6.1 estará terminada cuando:

- los formularios actuales con `data-omni-confirm` sigan funcionando;
- una acción JavaScript pueda solicitar confirmación;
- cancelar no ejecute la acción;
- confirmar ejecute exactamente una vez;
- no se rompa ninguna pantalla existente;
- `npm run build` pase.

# 6. P3.6.2 — Cambios sin guardar y navegación

## 6.1. Objetivo

Evitar que el usuario pierda cambios de configuración de Single Elimination al navegar dentro de OmniMerge.

---

## 6.2. Alcance

La lógica pertenecerá exclusivamente a:

```text
singleEliminationWorkspace
```

No se implementará un interceptor general para toda la aplicación.

---

## 6.3. Casos

### Caso A — navegación interna

```text
Editar regla
↓
dirty = true
↓
clic en Estructura
↓
OmniConfirm
```

Acciones:

```text
Seguir editando
Descartar y salir
```

---

### Caso B — botón Descartar

```text
Cambios locales
↓
Descartar
↓
OmniConfirm
↓
restaurar último estado persistido
```

---

### Caso C — F5 / cerrar pestaña

Se mantiene:

```text
beforeunload
```

como última defensa.

---

## 6.4. Navegaciones que no deben bloquearse

No deben interceptarse incorrectamente:

- Ctrl + clic;
- Cmd + clic;
- `_blank`;
- enlaces de descarga;
- `mailto:`;
- `tel:`;
- anchors locales cuando no implican salir;
- acciones ya confirmadas;
- submit de guardado.

---

## 6.5. Definition of Done

- dirty state detecta cambios reales;
- guardar no muestra aviso de abandono;
- descartar requiere confirmación;
- navegación interna requiere confirmación;
- cancelar conserva los valores;
- confirmar navega una única vez;
- F5 conserva el fallback del navegador.

# 7. P3.6.3 — Reglas, capability gating y Preview

## 7.1. Objetivo

Hacer que la pantalla de reglas comunique de manera exacta qué soporta Stable V1.

---

## 7.2. BASIC

El contrato estable BASIC es:

```text
Input:
POOL

Routing:
AUTOMATIC

Encounter:
DUEL

K → Q:
2 → 1

Remainder:
BYE o REJECT
```

Las opciones que no forman parte del contrato BASIC no deben presentarse como operativas.

---

## 7.3. ADVANCED

ADVANCED puede exponer capacidades adicionales, pero debe distinguir:

- configurables y ejecutables;
- configurables pero bloqueantes;
- todavía no soportadas.

---

## 7.4. Capability badges

Se normalizarán etiquetas como:

```text
Disponible
Requiere modo avanzado
Próximamente
No compatible
```

---

## 7.5. Preview

El Preview debe distinguir conceptualmente:

```text
IDLE
UPDATING
VALID
WARNING
ERROR
```

Estados visibles:

```text
Sin cambios
Cambios sin guardar
Actualizando vista previa
Vista previa válida
Vista previa con advertencias
Configuración incompatible
```

---

## 7.6. Diagnósticos

Separar:

### Error

Bloquea guardado o ejecución.

### Warning

No siempre bloquea, pero requiere atención.

### Recommendation

No bloquea. Es una mejora sugerida.

Nunca presentar warnings bajo el título “Recomendaciones”.

---

## 7.7. Guardado y Structure STALE

Si guardar reglas invalida una estructura previamente generada, el mensaje debe ser explícito.

Ejemplo:

```text
Configuración guardada.

La estructura existente quedó desactualizada.
Debes regenerarla o validarla antes de ejecutar.
```

---

## 7.8. Definition of Done

- BASIC no promete capacidades que no tiene;
- ADVANCED diferencia soporte real;
- Preview refleja cambios locales;
- errores y warnings no se mezclan;
- configuración guardada informa si Structure quedó STALE;
- interfaz conserva el diseño OmniMerge.

---

# 8. P3.6.4 — Structure statuses y diagnósticos

## 8.1. Objetivo

Representar de forma inequívoca el estado real del Structure Graph.

---

## 8.2. Estados oficiales

### NOT_GENERATED

```text
Sin estructura
```

Acción principal:

```text
Generar estructura
```

---

### GENERATED

```text
Estructura generada
Pendiente de validación
```

Acción:

```text
Validar
```

---

### VALID

```text
Lista para ejecutar
```

Debe utilizar una representación positiva.

---

### INVALID

```text
Contiene errores
```

Debe mostrar los errores bloqueantes.

---

### STALE

```text
Estructura desactualizada
```

Significa que las reglas actuales ya no corresponden con la estructura persistida.

---

### BLOCKED

```text
Estructura válida, pero no ejecutable
```

Este estado es especialmente importante.

Una estructura puede ser:

```text
structural_valid = true
```

pero:

```text
executable = false
```

por depender de una capacidad manual o personalizada que Stable V1 todavía no resuelve.

BLOCKED nunca debe utilizar el mismo tratamiento verde de VALID.

---

## 8.3. Diagnósticos

Se conservarán categorías separadas:

```text
Errores
Advertencias
Recomendaciones
```

Cada issue debe intentar comunicar:

```text
qué ocurrió
por qué importa
qué elemento afecta
qué puede hacer el usuario
```

---

## 8.4. No rediseñar el visualizador

P3.6.4 no tiene como objetivo reemplazar el visualizador actual.

Se conservarán:

- bloques;
- tablas;
- vistas compactas;
- inspector;
- workspace AUTO/CUSTOM/REVIEW.

El trabajo se limita a claridad de estado y acciones.

---

## 8.5. Definition of Done

Los seis estados son visualmente distinguibles y coherentes con el backend.

---

# 9. P3.6.5 — I/O Manager y Phase Exits

## 9.1. Objetivo

Hacer visibles los contratos de entrada y salida de la fase.

---

## 9.2. Input Gates

Las puertas de entrada deben mostrar, cuando esté disponible:

```text
nombre
tipo
capacidad
distribución
estado
cobertura
```

---

## 9.3. Phase Exits

Cada salida debería comunicar claramente:

```text
Nombre
Selector
Timing
Contrato
Modo de resolución
```

Ejemplo:

```text
Mejores semifinalistas

Selector
TOP_N · 2

Timing
Al finalizar la fase

Contrato
Exactamente 2

Resolution
Runtime selector
```

---

## 9.4. Labels de timing

```text
PHASE_END
→ Al finalizar la fase

ON_ELIMINATION
→ Al producirse la eliminación

ON_RULE_TRIGGER
→ Al activarse una regla
```

---

## 9.5. Eliminación

Eliminar una Phase Exit debe usar:

```text
OmniConfirm
```

y no un submit destructivo silencioso.

---

## 9.6. Definition of Done

- selector visible;
- timing visible;
- contrato visible;
- delete confirmado;
- no se rompe Structure;
- no se modifica todavía el Lab.

# 10. P3.6.6 — Competition Lab base, BYE y errores

## 10.1. Objetivo

Antes de mejorar Series o standings, estabilizar completamente la interfaz base del Competition Lab.

Esta etapa debe ser pequeña y observable.

---

## 10.2. Confirmaciones

Se reemplazarán confirmaciones nativas para:

```text
Reiniciar Lab
Cerrar Lab temporal
```

por OmniConfirm.

---

## 10.3. Reset

El modal debe explicar:

### Se elimina

- runtime temporal;
- scores;
- decisiones;
- series del Lab;
- progreso de simulación.

### Se conserva

- Tournament Template;
- Phase Templates;
- reglas persistidas;
- Structure Graph persistido.

---

## 10.4. Estados de Match

Debe distinguir:

```text
WAITING
PENDING
BYE
COMPLETED
```

### WAITING

Faltan participantes/dependencias.

### PENDING

Encuentro listo para resolverse.

### BYE

Avance automático sin competencia.

### COMPLETED

Encuentro resuelto.

---

## 10.5. BYE

Representación:

```text
Avanza por BYE

Este participante avanza sin disputar
un encuentro competitivo.
```

No debe mostrar:

- score falso;
- victoria competitiva;
- botón Guardar resultado;
- Game score.

---

## 10.6. Runtime bloqueado

Estados como:

```text
BLOCKED
STRANDED
OVER_CAPACITY
```

deben incluir una explicación.

Ejemplo:

```text
La simulación no puede continuar.

El nodo recibió más participantes
de los permitidos por su contrato.
```

---

## 10.7. Errores del Lab

En lugar de presentar todos los errores como una única cadena sin estructura, la UX debe diferenciar conceptualmente:

```text
Título
Categoría
Mensajes
Contexto
```

No es obligatorio cambiar inmediatamente el protocolo backend si el mismo resultado puede representarse de manera segura en frontend.

---

## 10.8. Protección de acciones

Mientras:

```text
loading = true
```

no deben enviarse acciones duplicadas.

---

## 10.9. Definition of Done

Antes de pasar a Series:

- Lab se renderiza completo;
- no hay errores Alpine;
- Reset funciona;
- Cerrar funciona;
- BYE es correcto;
- estados base son claros;
- errores se muestran;
- no hay doble submit.

---

# 11. P3.6.7 — Series, Games y placement bands

## 11.1. Objetivo

Representar de manera fiel el sistema de series ya implementado en P3.3.

---

## 11.2. Diferenciar Game y Series

Ejemplo BO5:

```text
Formato
BO5

Serie
Jugador A 2 – 1 Jugador B

Siguiente
Juego 4
```

Un Game individual puede tener:

```text
Juego 4

Jugador A 10 – 8 Jugador B
```

El score del Game no es el score de la Serie.

---

## 11.3. BEST_OF

Soportados:

```text
BO1
BO3
BO5
BO7
BO9
```

La interfaz puede mostrar:

```text
BO5
Primero en llegar a 3 victorias
```

---

## 11.4. FIXED_GAMES

Si:

```text
FIXED_GAMES = 4
```

se disputan obligatoriamente cuatro Games.

La serie no termina anticipadamente.

---

## 11.5. Sudden death

Si los Games nominales terminan empatados:

```text
2 – 2
```

debe aparecer:

```text
DESEMPATE

Los juegos nominales terminaron empatados.
El siguiente Game es sudden death.
```

Ejemplo:

```text
Siguiente
Desempate · Juego 5
```

---

## 11.6. Placement bands

Single Elimination no siempre produce posiciones individuales exactas.

La UX debe usar:

```text
position_from
position_to
```

Ejemplos:

```text
1.º
2.º
3.º–4.º
5.º–8.º
```

---

## 11.7. SURVIVORS

Si la fase termina con:

```text
target_survivors = 2
```

los dos supervivientes comparten:

```text
1.º–2.º
```

No debe inventarse:

```text
Campeón
Subcampeón
```

si no hubo una final competitiva 2 → 1.

---

## 11.8. Champion / Runner-up

“Campeón” solo corresponde cuando:

- fase completada;
- un único superviviente;
- posición exacta 1.

“Subcampeón” solo debe presentarse si existe una posición 2 demostrada por la estructura competitiva.

---

## 11.9. Standings de Single Elimination

La tabla genérica de ligas:

```text
PJ
Pts.
Dif.
```

no debe ser protagonista para Single Elimination.

Prioridad:

```text
Posición/banda
Participante
Estado
Eliminado en
Encuentro
Serie / resultado
```

---

## 11.10. Definition of Done

- BO correcto;
- FIXED_GAMES correcto;
- sudden death visible;
- Game ≠ Series;
- BYE no participa en Series;
- placement bands correctos;
- survivors no reciben ranking ficticio.

---

# 12. P3.6.8 — Decisiones manuales y cierre UX

## 12.1. Objetivo

Cerrar las interacciones donde el runtime necesita información explícita del usuario.

---

## 12.2. AWAITING_DECISION

Debe ser muy visible.

Ejemplo:

```text
Decisión necesaria para continuar
```

La simulación debe entenderse como pausada.

---

## 12.3. Selección exacta

Ejemplo:

```text
Selecciona 2 participantes

1 / 2
```

El botón de confirmar debe habilitarse solo cuando exista exactamente la cantidad requerida.

---

## 12.4. Orden manual

La UX debe mostrar claramente:

```text
Seed 1
Seed 2
Seed 3
...
```

cuando el orden represente seeding.

No limitarse a números sin contexto.

---

## 12.5. Group Assignment

Cada participante debe pertenecer a un grupo válido y la capacidad de los grupos debe coincidir con lo requerido.

---

## 12.6. Decisión stale

Si la decisión ya no corresponde con el runtime actual:

```text
Esta decisión ya no es válida para el estado actual.

Actualiza el Lab o reinicia la simulación.
```

No debe fallar silenciosamente.

---

## 12.7. Correcciones de resultados

Stable V1 mantiene la decisión:

> Un resultado ya propagado no se edita en caliente.

Si el usuario necesita corregirlo:

```text
Reinicia el Competition Lab.
```

La edición/historial oficial de resultados pertenece al futuro Tournament Runtime persistente.

# 15. Procedimiento estándar por cada parte

```powershell
git status --short
git rev-parse HEAD
```

---

## 15.2. Comprobar patch

```powershell
git apply --check .\OmniMerge-P3.6.X-....patch
```

---

## 15.3. Aplicar

```powershell
git apply .\OmniMerge-P3.6.X-....patch
```

---

## 15.4. Revisar diff

```powershell
git status --short
git diff --check
git diff --stat
git diff
```

# 20. Resumen final

La nueva estrategia de P3.6 prioriza **control de regresiones**.

Antes:

```text
muchos cambios
↓
un único patch
↓
difícil identificar qué rompe qué
```

Ahora:

```text
una responsabilidad
↓
un patch pequeño
↓
una prueba concreta
↓
un commit
↓
nuevo baseline
```

Orden definitivo:

```text
P3.6.1  OmniConfirm
P3.6.2  Unsaved navigation
P3.6.3  Reglas + Preview
P3.6.4  Structure
P3.6.5  I/O
P3.6.6  Lab base
P3.6.7  Series + placements
P3.6.8  Manual decisions + regression
```

Esta división mantiene todo el alcance original de P3.6, pero reduce el acoplamiento, facilita rollback y permite validar visualmente cada avance antes de continuar.
